# Manual curtain configurator and fabric catalogue

This implementation replaces whole-image prepared-look selection with independent browser-rendered main and sheer layers. The original comparison gesture, fonts, palette, API authentication, private storage and enquiry workflow are retained. No deployment, package installation or lockfile changes were made. All component layout and appearance stay in Tailwind TSX classes; globals.css was unchanged.

## Rendering and controls

`components/curtains/CurtainConfigurator.tsx` owns the layer controls, palettes, heading compatibility, surface study, room and summary. `ManualPreview.tsx` composites a local room photograph with two separately memoized Canvas 2D layers. Alpha cutouts retain photographic folds and edges; luminance-based recoloring preserves shadows. Sheer opacity reveals the window underneath. Main and sheer toggles preserve their selections. Material treatments adjust surface contrast, fine grain and translucency. Only the affected canvas repaints when its color changes; room changes replace the background without changing either curtain selection.

Six aligned backgrounds cover living room, bedroom, dining, office, guest and nursery. Eight optimized 1280×960 WebP assets (six rooms and two alpha layers) live in `public/images/curtains/manual/`. They were created using the **built-in imagegen skill/tool**, inspected, then copied/encoded into the repository. Original generated PNGs remain under the Codex generated_images directory. `scripts/manual-base-sources.json` records initial paths and exact prompts; `scripts/manual-room-sources.json` records room-edit paths and exact prompts. `scripts/prepare-manual-assets.cjs` performs local encoding.

These are **visual approximations**, not supplier-specific or color-calibrated fabric previews. The material grain and surface patterns are illustrative treatments. Six heading selections alter the top-band shading study, but do not render six physically different tailored heading geometries. Production-quality wave, pinch, eyelet, pencil, goblet and rod-pocket geometry needs separate aligned alpha/fold maps or validated meshes for each heading. Supplier-specific velvet pile, weave, blackout lining, measured translucency, accurate swatch photography and precise foreground occlusion masks also remain to be supplied. The interface explicitly labels these limits; no arbitrary combination is presented as an exact product photograph.

## Catalogue and missing supplier data

`lib/curtains/catalogue.ts` defines optional technical/commercial fields and color variants. `demo-catalogue.ts` is a clearly separated fixture with four main material directions and two sheer directions. Its limited material-specific palettes are explicitly labelled DEMO. Colors are not represented as available stock; variant availability is null. No width, GSM, composition percentages, prices, stock counts, certifications or lead times have been invented.

`supplier-catalogue.json` is intentionally empty. Import verified supplier records using `supplier-catalogue.schema.json`; omit unknown optional fields. Run `node scripts/validate-supplier-catalogue.cjs` before use. Validation also runs before dev/build, checks local asset paths and IDs, and requires usable main/sheer records for the layered experience. Use the stable collection ID as slug. Record manufacturer color codes and variant SKUs separately from display names and digital hex approximations. Include local licensed swatch/gallery photography when available. Do not treat schema validation as verification of supplier claims.

`components/curtains/CatalogueBrowser.tsx` uses the existing API catalogue, search, layer/category/color-family filters, results and empty states, plus a native mobile filter drawer. Verified composition, pattern, transparency, roll-width and GSM filters appear conditionally when imported supplier records supply those values. `TechnicalFilters.tsx` and `lib/curtains/catalogue-filters.ts` implement them; missing values do not match active numerical filters.

`FabricDetail.tsx` and `FabricSpecifications.tsx` add variant selection, digital swatches or supplied swatch photographs, gallery slots, all technical/commercial fields and functioning consultation links to existing `/collections/[id]` routes. Missing information reads **Specification pending**. Roll width is distinguished from finished curtain width; GSM from panel weight. Existing images remain reference photography. Verified variant photographs, close-ups and installation galleries are not yet available and are labelled accordingly. “Visualize This Fabric” applies the chosen material/color to its supported layer while preserving the other layer.

## State and Studio

`lib/curtains/manual-config.ts` validates/normalizes the shared configuration. Material changes retain the old color/heading when compatible; otherwise only that layer receives a valid default and the interface explains the change. The configuration persists in browser storage (`dcorhome-manual-v1`) and validated Studio URL parameters, including both material IDs, both colors, both headings, enabled flags, pattern and room. No state-management dependency was added.

Studio opens in sample mode by default. “Upload My Room” switches to the existing upload/AI workflow with the same selections. Duplicate unrestricted color controls were replaced with the shared layer controls; overall direction, length, fullness, upload, placement sketch, comparison, save/history, download, share and consultation remain. Studio updates its URL when selections change so refresh retains the latest choices.

`app/api/visualize/route.ts` validates sheer material/heading and enabled flags, rejects requests with both layers disabled, preserves the configuration in saved options and describes each enabled material/color/heading separately in the provider prompt. Manual changes make no AI request. The live service still depends on the existing server credentials/storage settings. Test generation uses an explicitly isolated mock provider, never a real paid API call.

## Verification

Commands: `npm run lint`, `npm run build`, `node scripts/manual-config-check.cjs`, `node scripts/api-check.cjs`, and headless Chrome checks with `DCORHOME_MANUAL_ONLY=true node scripts/browser-check.cjs` plus the full browser suite.

The focused browser tests compare actual canvas pixels: changing sheer color leaves main bytes unchanged and vice versa. They cover material palettes, heading response, layer disable/enable, persistence, detail-to-configurator transfer, the mobile drawer, meaningful empty results and 390/768/1024/1440 layouts. Screenshots are saved as `%TEMP%/dcorhome-manual-{width}.png`. The full suite checks existing routes, comparison autoplay, mouse/touch/keyboard controls, upload, local saves and consultation errors. The isolated API suite checks private persistence, upload decoding, prompt fields, layer validation and the existing generation/save/share/admin flows with a mock provider.

Final verification: TypeScript, production build, asset/model checks, focused manual browser scenarios, all 75 broad route/width checks, existing mouse/touch/keyboard interactions and isolated API/UI mock-provider tests passed. Focused tests confirmed all six room images change without altering either curtain canvas, zero AI POST requests during manual changes, and refreshed Studio URLs preserve the latest choices. Real-device low-end performance, physical swatch matching and live provider image quality remain unverified.
